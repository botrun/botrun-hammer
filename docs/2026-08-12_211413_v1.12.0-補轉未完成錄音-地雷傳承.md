## ⭐⭐⭐ L1（最重要）：錯誤訊息裡的每一句「你可以去 X 做 Y」都是規格，不是文案

v1.11.4 為了安撫使用者，在身分把關失敗的彈窗寫了：

```lua
"\n\n錄音已保留，登入後可從 F6 選單重轉",   -- botrun-hammer.lua:1292
```

但 F6 →「🎵 錄音檔案…」的實作只有：

```lua
hs.task.new("/usr/bin/open", nil, {"-R", choice.filePath}):start()   -- 只在 Finder 指給你看
```

**那個「重轉」功能從來不存在。** 使用者照著彈窗做，得到一個 Finder 視窗。

- 這比「什麼都不說」更傷：它把「這工具會騙我」寫進第一印象，而信任一旦破掉，
  之後每次錄音都要回頭確認，成本遠高於這次少轉的一段話。
- **通則**：撰寫引導文案時，那句話就是一條**未實作的規格**。
  凡是文案裡出現「按 X 可以 Y」，就必須有對應實作 ＋ 對應測試（本案 S1）。
- **反向自檢**（可直接抄）：`grep -oE '按 F[0-9]+[^"]*' *.lua` 把所有承諾撈出來，
  一句一句問「這件事真的做得到嗎？」

## ⭐⭐⭐ L2：事後補救的動作，絕對不能沿用「當下」的輸出方式

原流程轉錄完成 → `pasteText()` 模擬 ⌘V 貼到最前景 App。**那是對的**，因為錄完當下
游標就在你要貼的地方。

但**補轉是事後行為，時空已經錯位**：使用者按下補轉後可能人在 Terminal、聊天室、
或正在編輯的文件上。自動貼上輕則污染文件、誤送訊息，**重則在 Terminal 裡被當成指令執行**。

→ 補轉一律只 `hs.pasteboard.setContents()` ＋ 明講「請按 ⌘V」，把貼上的時機還給使用者。

### 附帶技巧：怎麼「動態」驗證「沒有自動貼上」
不能只靠讀程式碼（靜態檢查會被重構繞過）。利用既有實作的副作用當試紙：

`pasteText()` 會在貼上後 0.5 秒**把剪貼簿還原成舊值**；補轉只 setContents 不還原。
所以測試先塞一個哨兵字串，補轉完成後：

- 剪貼簿 == 哨兵 → 走了貼上路徑（**失敗**）
- 剪貼簿 == 轉錄文字 → 只有複製（**通過**）

一個既有的「還原行為」就成了免費的、無法被繞過的判別器。

## ⭐⭐⭐ L3：非同步回呼會遺失——批次流程一定要有監督者，「鎖死」比「少做一件」嚴重得多

實測 7 次批次補轉，**有 2 次卡住**：轉錄明明已經結束（ESC 熱鍵都解綁了），
但補轉的回呼再也沒回來，`running` 就永遠停在 `true`。

後果不是「少轉一筆」，而是**整個補轉功能從此按不動**——之後每次按 F6 都只會看到
「⏳ 批次補轉進行中…」，而那個批次早就死了。這是典型的
**局部故障升級成全域故障**。

**治本＝監督者（supervisor）**，判準用「外部可觀測事實」而非內部旗標：

```lua
-- 這一筆還在飛(inFlight)、但已經沒有任何轉錄在進行(isTranscribing=false)，
-- 連續 3 次（約 15 秒）都這樣 → 判定失聯，記為失敗並往下一筆
retranscribeState.supervisor = hs.timer.doEvery(5, function() ... end)
```

配套三件事，缺一不可：

1. **token 版號**：被監督者判失聯後推進，**遲到的回呼必須被忽略**，
   否則兩條鏈同時往前跑，計數全亂。
2. **timer 存進 state 保持強引用**（`retranscribeState.timer = hs.timer.doAfter(...)`）。
3. **失聯那筆的狀態要退回**（別留在 `transcribing`），使用者之後還能再補轉它。

> 排錯順序建議：先確保「一定會結束」，再去追「為什麼會遺失」。
> 前者保護使用者，後者是工程好奇心。

## ⭐⭐ L4：`hs -c` 的非同步 print 不會回到終端機——我因此誤判了三次

`hs -c 'xxx'` 只把**那一次求值的同步輸出**送回終端機。任何 callback／timer 之後才
`print` 的內容，只會進 Hammerspoon console。

我一開始看終端機沒有「回呼」那行，就判定「callback 沒回來」，**方向完全錯了**。

- 正確做法：`hs -c 'print(hs.console.getConsole())'` 讀 console（回傳的是 string，直接 print 即可）。
- 更可靠：關鍵狀態不要用 print 觀察，**開一個同步查詢 API**（本案 `_G.botrunHammer.retranscribeStatus()`
  回傳 `running/index/total/ok/fail`），一行就看到全貌，不受非同步輸出通道影響。
- 附帶：在 `hs -c` 裡臨時建立的 closure 當 callback 會噴 `LuaSkin: hs.task callback:` 空錯誤，
  **不要用這種方式驗證 callback 行為**，結論會是假的。

## ⭐⭐ L5：殘留狀態會讓「重跑」靜默不執行，害你追一個早就不存在的 bug

第一次卡住後，我直接重跑批次驗證，看到 `index=4 ok=3` 一動也不動，
以為又卡在同一個地方。**其實那次根本沒有啟動**——`running` 還是上一輪的 `true`，
`retranscribeAllPending()` 開頭就 `return` 了，我讀到的是**上一輪的殘影**。

- **通則**：每次重現實驗前，先把狀態歸零（本案＝`hs.reload()`），
  並且**先印一次狀態確認是乾淨的**再開始。
- 提早採用 L3 的監督者也會順帶消滅這種殘留狀態。

## ⭐⭐ L6：bash 變數後面直接接全形字元 → `unbound variable`（中文腳本專屬地雷）

```bash
info "測試音檔完成（voice=$VOICE）"     # ❌ VOICE） 被當成變數名 → unbound variable
info "測試音檔完成（voice=${VOICE}）"   # ✅
```

bash 在解析 `$NAME` 時不會在多位元組字元邊界停下來，`）`「」等全形標點會被吃進變數名。
用 `set -u` 時直接爆炸，沒用 `set -u` 時**更慘：靜默變成空字串**。

一次修好全檔：

```bash
perl -CSD -i -pe 's/\$([A-Za-z_][A-Za-z0-9_]*)(?=[^\x00-\x7F])/\${$1}/g' your_script.sh
```

**寫中文訊息的 shell 腳本，變數一律用 `${VAR}` 形式**，別賭它後面接的是什麼。

## ⭐ L7：`hs -c` 首次載入 extension 會把 `-- Loading extension: json` 混進 stdout

```
測試開始前既有 pending 數 = -- Loading extension: json
0
```

取值變成兩行，之後所有數值比較全錯，而且**錯得很像業務邏輯壞掉**。

```bash
hsc() { hs -c "$1" 2>/dev/null | grep -v '^-- Loading extension:'; }
```

初始化／進度／警告行；濾掉再用。

## ⭐ L8：FIFO 歷史淘汰必須保護「待處理」項，否則資料會變孤兒

`history.json` 只留 30 筆，但錄音檔永久保留（本機已 2683 個檔、4.4 GB）。
舊版淘汰邏輯直接砍尾端：重度使用者 30 筆一輪，**待補轉的紀錄就被沖出歷史**，
音檔還躺在資料夾裡卻再也沒有索引找得到它 ＝ 實質永久遺失。

```lua
while #history > config.maxHistory do
  local removeIdx = nil
  for i = #history, 1, -1 do
    if not isPendingEntry(history[i]) then removeIdx = i break end   -- 跳過待處理項
  end
  if not removeIdx then break end   -- 全是待處理：寧可超出上限，也不丟資料
  table.remove(history, removeIdx)
end
```

**通則**：任何有上限的佇列／快取，淘汰策略都要問一句
「**被淘汰的那筆，是不是還有未完成的義務？**」有的話就不能只看新舊。
