# v1.11.2 — 「另一台機器可以、這台不行」debug 實錄：anaconda PATH 污染二連擊

日期：2026-07-23｜機器：Apple M3 Max（arm64）｜症狀：gemini ADC 雲端轉錄失敗、breeze/lwm 本機引擎裝不起來

## TL;DR

同一份程式、同一個 ADC 帳號，另一台機器正常、這台全掛。根因**不是認證、不是權限、不是程式**，
是這台機器的 `~/opt/anaconda3/bin` 排在 PATH 最前面，用兩顆「x86_64 老工具」蓋掉了系統/homebrew 的原生工具：

| 症狀 | 被蓋掉的工具 | 元凶 | 錯誤表象 |
|---|---|---|---|
| gemini ADC 轉錄失敗 | `/usr/bin/curl` 8.4（HTTP/2） | anaconda `curl` 7.68（HTTP/1.1, x86_64/darwin13） | HTTP **417** + Google「automated queries」HTML 封鎖頁 |
| breeze/mlx 安裝失敗 | homebrew `uv`（aarch64） | anaconda `uv`（x86_64） | venv 建成 x86_64 Python → `mlx` 只出 arm64 wheel → `unsatisfiable` |

## Debug 過程（照時間軸）

1. **先驗認證**：`gcloud auth application-default print-access-token` OK；tokeninfo 查出 ADC 是
   `chiamin76@cameo.tw`（@cameo.tw 網域已授權）、scope 含 cloud-platform → **認證面全部正常，排除 403 假說**。
2. **脫離 Hammerspoon、用 shell 重放 lua 的完整請求**（ffmpeg→opus→base64→jq→curl POST Vertex）：
   得到 **HTTP 417** 和一頁 Google「We're sorry... automated queries」HTML——不是 Vertex 的 JSON 錯誤。
3. **417 = Expect: 100-continue 被拒**。curl 對 >1KB 的 POST body 會自動加 `Expect: 100-continue`
   header；Google 前端（GFE）不吃這招，直接 417。加 `-H "Expect:"` 後**立刻 200、轉錄成功**。
4. **為什麼另一台機器沒事？** `which -a curl` → `~/opt/anaconda3/bin/curl` 是 **curl 7.68.0
   （x86_64-apple-darwin13）**，走 HTTP/1.1 才會送 Expect；系統 `/usr/bin/curl` 8.4 走 HTTP/2
   （nghttp2）根本不送 Expect。另一台機器 PATH 沒有 anaconda curl，所以永遠沒踩到。
5. **breeze/lwm 同根病**：`lwm_daemon_ctl.sh install` 報 `mlx unsatisfiable`。機器明明是 M3 Max，
   卻查出 venv Python 是 **x86_64**——因為 anaconda 的 x86_64 `uv` 蓋掉 homebrew 的 aarch64 `uv`，
   x86_64 uv（Rosetta 下自認 Intel）建出 x86_64 venv，而 mlx 只發佈 arm64 wheel。
6. **附帶發現**：lua 沒有 `require("hs.ipc")`，`hs -c` 連不上 message port，E2E 自動化跑不了。

## 修法（v1.11.2，全部走「相容多數安裝情況」原則）

### hammerspoon/botrun-hammer.lua
- Vertex 呼叫改 `CURL=/usr/bin/curl`（不存在才退回 PATH 的 curl），且**無論哪顆 curl 都加
  `-H "Expect:"`**——新舊 curl、有無 anaconda、Intel/Apple Silicon 全都能動。
- 加 `pcall(function() require("hs.ipc") end)`，讓 `hs -c` E2E 驗證入口恢復可用。
- 版本 1.11.1 → 1.11.2。

### scripts/lwm_daemon_ctl.sh
- `pick_uv()`：掃 `/opt/homebrew/bin`、`/usr/local/bin`、`~/.local/bin`、`~/.cargo/bin`、PATH，
  **優先挑「架構＝`uname -m`」的 uv**；沒原生的就從 astral.sh 裝（官方安裝器必裝原生版）；
  真的只有非原生 uv 也退回可用（Intel 機器不受影響）。
- `venv_arch_matches()`：venv Python 架構不符機器 → 自動備份重建（沿用 v1.8.0 migrate 哲學，
  同事不用手動清理）。
- 新增 `install-breeze` 指令：裝 `transformers torch accelerate`（breeze fp32 依賴），
  獨立於基本 install，不強迫只用雲端的使用者吃 ~3GB。

## 跨專案地雷（傳承）

- **L1「另一台可以、這台不行」先懷疑 PATH，不是先懷疑程式**：`which -a <tool>` + `file <binary>`
  兩條指令就能揪出被蓋掉的工具；anaconda 是最常見污染源（curl/uv/python/openssl 全套 x86_64 老件）。
- **L2 分發出去的腳本不能信 PATH 上的第一顆工具**：要嘛固定絕對路徑（`/usr/bin/curl`）、
  要嘛按「架構相符」挑選（uv），並保留 fallback 維持相容性。
- **L3 HTTP 417 + Google HTML sorry page ＝ curl 的 `Expect: 100-continue` 被 GFE 拒絕**，
  跟認證/權限完全無關；解法一行 `-H "Expect:"`，且對新 curl 無副作用（新 curl 本來就不送）。
- **L4 Apple Silicon 上的 x86_64 工具鏈是隱形炸彈**：Rosetta 讓它「能跑」，但它建出的一切
  （venv、wheel 選擇）都是 x86_64，撞上 arm64-only 套件（mlx）才爆。自我修復要驗「架構」不只驗「存在」。
- **L5 E2E 自動化入口（hs.ipc）也要進版本控管**：缺一行 `require("hs.ipc")`，所有 `hs -c`
  驗證 SOP 全部失效，而且錯誤訊息（message port）完全看不出是少 require。
