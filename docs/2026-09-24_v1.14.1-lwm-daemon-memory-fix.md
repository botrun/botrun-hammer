# v1.14.1（daemon 1.11.1）lwm_daemon 記憶體修補：閒置占 20 GB 不還

日期：2026-09-24。機器：Mac14,9（M2 Pro、32 GB）、macOS 15.7.3、mlx 0.31.2、mlx_whisper 0.4.3。版號：lua `VERSION` 1.14.0 → 1.14.1、daemon `DAEMON_VERSION` 1.11.0 → 1.11.1、lua `LWM_DAEMON_REQUIRED_VERSION` 同步為 1.11.1。

## 問題

daemon 連續跑 28 天、轉錄 106 次後，閒置時 footprint 仍有 20.44 GB，占當時全機 footprint 的 40%，系統長時間處於記憶體壓力黃燈（壓縮器 16.45 GiB、free 0.21 GiB）。Python 自己的 malloc 只有 83.5 MB，其餘全在 MLX 的 Metal 緩衝快取。

三個原因：

1. MLX 的快取沒設上限。mlx 0.31.2 `set_cache_limit` 的說明：「The cache limit defaults to the memory limit」；`set_memory_limit`：「the memory limit defaults to 1.5 times the maximum recommended working set size reported by the device」。在這台 32 GB 機器上實測預設值是 30.4 GB（daemon log：`[mlx] cache limit 30.4 GB -> 1024 MB`），接近實體記憶體，等於沒有上限。每次轉錄配的緩衝用完進快取、從不還給 macOS，音檔長度不同、緩衝大小不同，快取只增不減。
2. 權重載了兩份。`WhisperBackend.load()` 自己 `load_model(repo)` 一份，`transcribe()` 又呼叫 `mlx_whisper.transcribe(path_or_hf_repo=repo)`，後者內部的 `ModelHolder` 再載一份；自己載的那份從未被用到。
3. 載了就不放。沒有閒置卸載，權重留到 daemon 重啟為止。

## 修法（DAEMON_VERSION 1.11.0 → 1.11.1）

| 改動 | 位置 | 說明 |
|---|---|---|
| `mlx_set_cache_limit(MLX_CACHE_LIMIT_MB)` | `main()` | 預設 1024 MB，環境變數 `LWM_MLX_CACHE_LIMIT_MB` 可調 |
| `mlx_clear_cache()` | `WhisperBackend.transcribe()`、`GemmaAudioBackend.transcribe()` | 每次轉錄後立刻清快取 |
| 拿掉自己的 `load_model()` | `WhisperBackend.load()` | 改成暖 `mlx_whisper.transcribe.ModelHolder`（與 `transcribe()` 預設 fp16 同一份） |
| `Backend.unload()`、`BackendCache.unload_if_idle()` | 新增 | 預設 1800 秒沒轉錄就放掉所有 backend 權重與快取；`LWM_IDLE_UNLOAD_SEC=0` 關閉。whisper 的權重在 `ModelHolder` 裡，重建 backend 物件放不掉，要明確設 `ModelHolder.model = None` |
| `/health` 多三個欄位 | `do_GET` | `mlx_active_mb`、`mlx_cache_mb`、`mlx_peak_mb`，方便量測 |
| `shutdown()` 改在另一條執行緒呼叫 `server.shutdown()` | `main()` | 舊寫法在 `serve_forever()` 的執行緒裡呼叫會互等卡死，`lwm_daemon_ctl.sh stop` 每次都等到 TERM timeout 才 KILL |
| `_env_int()` | 模組層 | `LWM_MLX_CACHE_LIMIT_MB`、`LWM_IDLE_UNLOAD_SEC`、`LWM_IDLE_CHECK_SEC` 亂填（非整數、負數）時記 log 退回預設值，daemon 照常啟動 |
| `LWM_IDLE_CHECK_SEC` | `main()` | 看門檢查間隔（預設 60 秒，下限 1），讓閒置卸載可以在測試裡幾秒內驗證 |
| backend 切換先放舊的再載新的 | `BackendCache._load_impl()`、`WhisperBackend.load()` | 切換 backend 或同 backend 換模型時，先 `unload()`＋`gc.collect()`＋`clear_cache()` 再載新模型，避免兩份權重同時在記憶體裡的尖峰；`BreezeBackend.unload()` 順手 `torch.mps.empty_cache()`（未實測） |
| lua `LWM_DAEMON_REQUIRED_VERSION` 1.11.0 → 1.11.1、lua `VERSION` 1.14.0 → 1.14.1 | `hammerspoon/botrun-hammer.lua` | lua 用 `ver ~= REQUIRED` 決定要不要重抓 daemon（第 1778 行），不同步的話同事拿不到修補、作者本機每次載入都重抓重啟；auto-update 只接受更大的 lua 版號，不升 lua 版本新 lua 推不到同事 |

MLX 沒裝、或 Metal 初始化失敗的環境（純 breeze 或雲端），所有 MLX 呼叫都會略過並記一次 log，`/health` 仍回 200，不影響其他 backend。

`WhisperBackend.load()` 暖模型時只把 `ImportError`／`AttributeError`（mlx_whisper 版本不同、沒有 `ModelHolder`）降級成延後載入；離線、repo 打錯這類真正的載入失敗會往上拋，`/switch_model` 不會假裝成功。

## 驗證

同一批音檔（`say -v Meijia` 合成的 29.8 秒、104.9 秒、225.0 秒三檔）連續轉錄 8 次，每次量 `top -l 1 -pid <pid> -stats mem`。

| 項目 | 1.11.0 | 1.11.1 |
|---|---|---|
| 啟動時 | 17 MB | 21 MB |
| 轉錄 1 次後 | 7,667 MB | 3,143 MB |
| 轉錄 2 次後 | 11 GB | 3,144 MB |
| 轉錄 8 次後 | 11 GB | 3,147 MB（MLX active 2,944.5 MB＝模型本身，cache 0） |
| 閒置卸載後 | 不會卸載 | 187 MB（測試時 `LWM_IDLE_UNLOAD_SEC=120`；卸載後再轉錄 4.8 秒重新載入，輸出相同） |
| 8 次耗時（秒） | 9／14／29／15／3／29／14／28 | 6／15／29／15／3／30／14／30 |
| `lwm_daemon_ctl.sh stop` | 等到 TERM timeout 才 KILL | 1 秒內（實測 0.6–0.7 秒，`serve_forever` 每 0.5 秒檢查一次） |

`scripts/test_lwm_daemon.sh` 新增 Stage C：`/health` 的 MLX 欄位與 cache 為 0、閒置卸載（測試用 `LWM_IDLE_UNLOAD_SEC=3`、`LWM_IDLE_CHECK_SEC=1`）、卸載後重新轉錄、SIGTERM 後 2 秒內結束且 pid／port 檔清掉、環境變數亂填仍能啟動。

## 已知問題（本次未處理）

重啟 daemon 時實測出現兩支 daemon（18120、18121）並存，同一秒啟動、pid 只差 3，pid 檔指向後起的那支。log 看起來是兩個呼叫端同時 `start`，但還沒查明是哪兩個（lua 裡 30 秒的是錄音 heartbeat logger、watchdog 是 60 秒，都不是直接呼叫 `ensure`）。建議 `ensure`／`start` 共用一個檔案鎖，或 `start` 先寫 pid 檔再啟動。

## 量測方式（給之後回歸用）

```bash
TOK=$(cat ~/.botrun-hammer/lwm.token); PORT=$(cat ~/.botrun-hammer/lwm.port); PID=$(cat ~/.botrun-hammer/lwm.pid)
curl -s -H "Authorization: Bearer $TOK" http://127.0.0.1:$PORT/health | jq '{model_loaded,mlx_active_mb,mlx_cache_mb}'
top -l 1 -pid $PID -stats pid,mem | tail -1
```
