白話比喻：換引擎前先查原廠型錄確認新引擎編號，不憑印象。（真操作：WebSearch + 官方 ai.google.dev 確認 stable id 是 gemini-3.5-flash、GA、支援音訊輸入 → 改 lua 第 44 行 → VERSION 1.9.3→1.9.4 → hs -c "hs.reload()"。）

v3（004+005）查 thinking 最小化的「正確參數」

白話比喻：想叫廚師別想太多、快點上菜——但得用菜單上真的存在的暗號。（真操作：查官方 thinking 文件——Gemini 3.x 用 thinkingLevel，合法值 MINIMAL/LOW/MEDIUM/HIGH，預設 medium、無法完全關閉；舊的 thinkingBudget: 0 是 2.5 世代語法，3.x 兩者同給會直接 400。）

v4（006+007+008）查上傳流程 →「一樣就不用改」

白話比喻：搬新家前先確認舊鑰匙能不能開新門——能開就別換鎖。（真操作：查證 Files API resumable 兩段式上傳（init 拿 upload_url → 上傳拿 file_uri → 帶進 generateContent）對 3.5 Flash 完全沒變；且程式碼裡 本來就寫好 thinkingConfig.thinkingLevel: "MINIMAL"，語法正確。結論：thinking 與上傳兩處都零修改。）

v5（003+009）部署 → commit → push → tag → GitHub Release

白話比喻：菜煮好不只端上自家桌，還要送到每位訂戶家門口。（真操作：git fetch origin main 先拉最新 → commit 2f8eebc push main → 順手把殘留的 docs/test-logs/ 加進 .gitignore（commit 衛生鐵律）→ git tag v1.9.4 → gh release create v1.9.4。同事端靠每 4 小時自動更新從 GitHub raw 收到。）

💡 為什麼最後突破（關鍵變因）

本次沒有「卡關」，關鍵變因是把查證當成第一級任務：使用者連下三道「上網查清楚再動」的指令（002/004/006），結果三項查證中兩項證明「原碼已正確、免改」。若憑記憶改，最可能的錯是把 2.5 世代的 thinkingBudget: 0 塞進 3.x 請求——官方明載會直接 400，等於升級當下把整條轉錄鏈打斷。先前版本不是卡關而是風險潛伏：preview model id 隨時可能被 Google 下架，趁 GA 出現即刻切換是零成本保險。

⚠️ 地雷清單

  • Gemini 3.x 禁止 thinkingLevel 與 thinkingBudget 並用：同請求給兩個直接 400。3.x 一律用 thinkingLevel（MINIMAL/LOW/MEDIUM/HIGH），且無法完全關閉 thinking，MINIMAL 就是地板。
  • Gemini 3.x 官方建議移除 temperature/top_p/top_k：舊參數別再帶。
  • preview model id 是定時炸彈：GA 版一出就該切，release note 標明來源文件連結方便日後稽核。
  • hs.reload 時 CLI 回「message port was invalidated」是正常現象：reload 本來就會斷 IPC，不是失敗；隔 3 秒再打 hs -c 驗證即可。
  • ~/.hammerspoon/botrun-hammer.lua 是 symlink 指向 repo：改 repo 檔案＋reload 即生效，不需 install.sh；但同事端要靠 push main 才收得到。
