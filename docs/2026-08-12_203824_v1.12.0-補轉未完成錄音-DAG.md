## 0. 現場證據（不是假設，是今天真的發生）

```
history.json 30 筆：done 27 / failed 3
2026-08-12 08:32:09  failed  2026-08-12_08-28-56.m4a  exists=True  text=(空)
2026-08-12 08:34:12  done    2026-08-12_08-34-10.m4a  exists=True  text="請幫我執行…"
```

錄音資料夾：**2683 個檔、4.4 GB**，`keepSuccessfulRecordings = true` → 音檔從不刪。
也就是說：**聲音一直都在，只是沒有任何一條路徑可以把它再送去轉錄。**

### 🔥 最痛的一刀：程式已經「口頭承諾」了一個不存在的功能

`hammerspoon/botrun-hammer.lua:1292`（v1.11.4 身分把關彈窗）：

```lua
"\n\n錄音已保留，登入後可從 F6 選單重轉",
```

但 F6 →「🎵 錄音檔案…」的實際行為是 `botrun-hammer.lua:2123`：

```lua
hs.task.new("/usr/bin/open", nil, {"-R", choice.filePath}):start()   -- 只在 Finder 裡指給你看
```

**使用者照著彈窗做，F6 進去，只得到一個 Finder 視窗。** 這比沒有提示更傷——
它把「工具會騙我」寫進了第一印象。這是本案要修的真正缺口（broken promise gap）。

## 1. 需求背後的五點動機

| # | 表層需求 | 背後真正動機 |
|---|---------|-------------|
| 1 | 「想再轉一次」 | **講過的話回不來**。語音是一次性思緒，重講一次不只花時間，講出來的內容還會不一樣（那個當下的靈感沒了）——這是不可逆損失，不是效率問題 |
| 2 | 「沒有地方讓我轉」 | **要的是主導權**：我知道檔案還在，我要能自己決定什麼時候救它，而不是求系統剛好幫我 |
| 3 | 「登入之後」 | **失敗與修復之間有時間差**。修好授權的那一刻，腦袋已經離開錄音現場了；系統必須替我記得「還有東西沒轉」 |
| 4 | （沒說出口）擔心 | **信任**：一次靜默失敗就會讓人開始懷疑「它是不是一直在吃掉我的話」，之後每次錄音都要回頭確認。信任成本遠高於這次的損失 |
| 5 | （沒說出口）同事 | **第一印象**：同事第一次裝完必定還沒跑 ADC login → 第一次錄音必失敗。若第一次失敗＝資料實質作廢，這個工具在他心裡就死了 |

## 2. 換位思考：兩種使用者、兩種痛

**A. 波哥（重度使用者，一天數十次、有 5 小時長錄音）**
- 痛點：長錄音失敗損失最慘（無法重講）；30 筆 FIFO 會把失敗紀錄擠掉 → 音檔變成 2683 個檔裡的孤兒，等於永久遺失
- 價值創造：pending 項目**免疫於 FIFO 淘汰** + F6 一眼看到「還有 N 筆沒轉」

**B. @cameo.tw 同事（第一次安裝）**
- 痛點：第一次錄音 100% 失敗（ADC 未登入是必經狀態），彈窗叫他去 F6，F6 卻沒有那個功能
- 價值創造：登入後回來按 F6 → 第一列就是「🔁 補轉 1 筆未完成錄音」→ 一鍵救回，第一印象從「會騙我」翻成「它替我記得」

## 3. 三個替代方案・多維度打分

評分維度（1–10，權重）：使用者痛點解決 ×3、發現性 discoverability ×2、KISS/實作風險 ×2、SSOT/架構契合 ×2、誤觸與副作用風險 ×1。

### 方案 A：歷史選單加「重新轉錄」動作（手動、明確）
F6 →「🎵 錄音檔案…」選中未完成的那筆即重轉；另加「🔁 補轉 N 筆…」批次入口。

| 維度 | 分 | 理由 |
|---|---|---|
| 痛點解決 ×3 | 9 | 完全解決「沒有地方可以再轉」，且可挑單筆 |
| 發現性 ×2 | 8 | 就在彈窗指引的 F6，且 N>0 時置頂；零狀態不干擾 |
| KISS ×2 | 9 | 復用既有 `transcribe()`／`loadHistory()`，無新資料檔 |
| SSOT ×2 | 9 | pending 直接由 `history.json` 的 `status` 推導，不另建佇列（唯一真相） |
| 誤觸 ×1 | 8 | 使用者主動觸發，不會無預警花錢／吃 CPU |
| **加權總分** | **8.8** | |

### 方案 B：Outbox 佇列 ＋ 背景自動重試（全自動）
另建 pending queue 檔，watchdog 偵測 ADC 恢復即自動指數退避重轉。

| 維度 | 分 | 理由 |
|---|---|---|
| 痛點解決 ×3 | 9 | 使用者完全不用動 |
| 發現性 ×2 | 4 | **無感也是一種風險**：轉好了不知道、貼到哪也不知道 |
| KISS ×2 | 3 | 新增佇列檔＋退避排程＋併發控制；與既有 `state.isTranscribing` 單工模型衝突 |
| SSOT ×2 | 4 | queue 檔與 history.json **兩份真相**，同步失敗就永遠對不起來 |
| 誤觸 ×1 | 3 | 背景批次打 Vertex＝無預警費用；長錄音可能連轉數十分鐘 |
| **加權總分** | **5.4** | |

### 方案 C：拖放任意音檔進來轉錄（通用檔案匯入）
新增 drop zone／選檔對話框，任意 m4a/mp3 皆可轉。

| 維度 | 分 | 理由 |
|---|---|---|
| 痛點解決 ×3 | 6 | 能救，但要**使用者自己去 2683 個檔裡找出是哪一個**——這正是他想避免的事 |
| 發現性 ×2 | 5 | 需要另立 UI 入口，且與「歷史」心智模型分離 |
| KISS ×2 | 6 | 要處理任意格式／時長／來源 |
| SSOT ×2 | 6 | 外部檔案要不要進 history？語意變模糊 |
| 誤觸 ×1 | 7 | 低 |
| **加權總分** | **5.9** | |

### 🏆 勝出：方案 A（8.8），並吸收 B 的**一個**優點
- 吸收：**在對的時機主動提醒**——每當一次轉錄成功（＝此刻身分確定可用），若仍有 pending，就提示「還有 N 筆未轉，F6 可補」。拿到 B 的「替我記得」，不吃 B 的「無預警背景執行」。
- 捨棄：背景自動重轉、指數退避、獨立佇列檔（過度工程，且違反 SSOT）。

### 業界對照（2026 現況）
- **Superwhisper**：History →（右鍵）**Process Again**，用當前 mode 重跑。→ 我們也支援右鍵重轉「已完成」的那筆（換引擎重轉的合法需求）。
- **OpenSuperWhisper**：明言 *"failed dictations keep their audio with a retry button instead of vanishing"*。→ 我們的音檔**早就留著了**，缺的正是那顆 retry button。
- **Outbox / DLQ 模式**：業界標準是「持久化佇列＋退避重試」，但那是**伺服器端無人值守**場景；桌面單人工具的等價物是「持久化狀態（我們已有 history.status）＋人類按下重試」，不必搬整套 DLQ。

## 4. 關鍵 UX 設計決策（含一顆地雷）

### 💣 地雷：補轉完成**絕對不可以**自動貼上
原流程 `toggleRecording()` 成功後呼叫 `pasteText(text)`（模擬 Cmd+V 貼到最前景 App）——那是對的，因為「錄完當下」游標就在你要貼的地方。

但**補轉是事後行為**：時空已經錯位。使用者按下補轉後，很可能切去 Terminal、Slack、或正在打字。此時自動貼上 ＝
- 貼進 Terminal → 可能**直接被當指令執行**
- 貼進聊天室 → 誤送出
- 貼進正在編輯的文件 → 破壞內容

→ **補轉一律只 `hs.pasteboard.setContents()` ＋ alert 告知，不 paste。** 要貼由使用者自己 Cmd+V。

### 決策二：pending 的唯一定義（SSOT）
`status ∈ {failed, cancelled, transcribing} 且音檔仍存在` ＝ pending。
（`transcribing` 也算：Hammerspoon 重載／當機會讓紀錄永遠卡在 transcribing，正是需要救的狀態。）

### 決策三：pending 免疫 FIFO 淘汰
`addToHistory` 淘汰時**從尾端跳過 pending 項**，只淘汰已完成的。否則重度使用者 30 筆一輪就把待救錄音沖掉 → 變孤兒檔。

### 決策四：零狀態不加雜訊
`N == 0` 時 F6 選單**不顯示**補轉列（v1.7.14 教訓：多餘的按鈕反而暗示系統不可靠）。

    並且 文字應在剪貼簿中

    當 我在「🎵 錄音檔案…」清單中對它按右鍵
    那麼 它應以「目前選定的引擎」重新轉錄（對齊 Superwhisper「Process Again」）

## 8. 執行結果（2026-08-12 21:14 台灣時間）

**`scripts/test_retranscribe.sh`：20 項全過、0 失敗**（真實 Vertex AI 轉錄，非模擬）

實作過程中新增了規劃時沒預見的 **S8**，原因如下：

### 追加的 S8：批次一定要會結束
實測 7 次批次補轉**有 2 次卡住**——轉錄明明結束了，補轉的回呼再也沒回來，
`running` 永遠停在 `true` → 之後按 F6 只會看到「進行中…」，**整個補轉功能從此按不動**。
局部故障升級成全域故障，比少轉一筆嚴重得多。

治本：加**監督者**（每 5 秒檢查；「還在飛但已無轉錄進行」連續 3 次即判失聯、記失敗並推進），
配套 token 版號防遲到回呼重複計數、timer 存進 state 保持強引用、失聯那筆狀態退回可再補轉。

### 順手修掉的相關缺陷
認證類錯誤（未登入／權限不足／身分被擋）原本仍會重試一次，並彈出
「⚠️ Gemini 暫時故障，重試中…」——**明明是沒登入卻怪到 Gemini 頭上**，
且讓批次的 fail-fast 慢一倍。改為認證類錯誤不重試（`isAuthError()`）。

### 真實世界成效
執行 E2E 當下，本機 `pending = 3`——使用者有 3 筆錄音躺著沒救。全部補轉成功：

| 2026-08-09_07-46-59.m4a | 155 秒 | ✅ 994 字元 |

## 7. 不做什麼（明確排除，避免範圍蔓延）

- ❌ 背景自動重轉（費用與驚訝成本；見方案 B 評分）
- ❌ 另建 pending queue 檔（違反 SSOT）
- ❌ 新增快捷鍵（v1.7.15 已統一 F6，不再增加記憶負擔）
- ❌ 掃描 2683 個孤兒音檔做「全域補轉」（history 之外的檔案沒有語境，且會誤轉幾百個舊檔）
