波特槌加入 Breeze-ASR-26 全精度（fp32）本機引擎
—— 一次把「模型選型、真假驗證、發布缺口」三件事做到底

本次替波特槌（Mac 語音轉文字工具）新增聯發創新基地的 Breeze-ASR-26 台語模型， 以 fp32 全精度在 Apple Silicon 本機執行。過程有三個值得傳承的節點： ①「全精度」為何不是走既有的 MLX 而是走 PyTorch transformers； ②使用者當場質疑「這真的是 fp32 嗎、怎麼這麼快」，我們用三方對帳把它證明成硬事實； ③要「發布給同事下載」時，抓出一個隱蔽的發布缺口——同事會拿到新選單卻配到舊引擎而報錯，並做了自動化治本。

二、依時間軸的演進：做法 → 結果 → 為什麼這樣走

v1 — 先掃描既有架構，找到「加一個引擎」的正確接點

白話比喻：要在一間已經營運的餐廳多加一道新菜，先看清楚廚房是怎麼分工的——誰負責點單、誰負責出菜——照它原本的規矩加，而不是自己另起爐灶。 （真操作：本機 STT 走 scripts/lwm_daemon.py，是一個 Backend 介面 + BackendCache 依模型名路由的 dispatcher；既有 WhisperBackend（mlx-whisper）與 GemmaAudioBackend（mlx-vlm）。加新引擎＝實作一個新的 Backend 子類，不動既有兩條路徑。）

v2 — 關鍵選型：「全精度」為什麼不是 MLX 而是 transformers

白話比喻：「原汁原味」的食材，供應商只出「新鮮整塊」的版本，沒有出「壓縮成罐頭」的版本。你想要原汁原味，就只能買整塊、自己下鍋，不能拿罐頭來假裝。 （真操作：查 HuggingFace，MediaTek-Research/Breeze-ASR-26 基於 openai/whisper-large-v2 微調，官方只出 F32 safetensors，沒有官方 MLX 權重。所以「全精度」＝直接載 F32、走 transformers pipeline，在 Apple Silicon 用 device="mps" + torch_dtype=torch.float32，完全不量化。既有的 mlx-whisper 反而做不到這件事。）

v3 — 實作 BreezeBackend 與三路路由重構

白話比喻：原本廚房只有兩個爐口，現在要放第三個爐口。與其每次都寫死「如果是 A 爐就關 B 爐」，不如改成一個爐口清單，「點哪個就開哪個、其餘關火」，以後加第四個爐口也不用再改判斷。 （真操作：新增 BreezeBackend（懶載入 torch/transformers、MPS/CPU 自適應、chunk_length_s=28 + return_timestamps=True 支援長音檔切塊）；把 BackendCache 從寫死兩 backend 重構成工廠 dict（whisper / gemma / breeze 三路），切換模型時釋放非當前 backend 的權重。daemon DAEMON_VERSION 1.9.0 → 1.11.0。）

v4 — 使用者當場質疑：「這真的是 fp32 嗎？怎麼全精度還這麼快？」

白話比喻：有人跟你說「這是純金」，你不能只聽他嘴巴講。要秤重、要看成色、要算體積——三個獨立的量測都指向同一個答案，才叫證明。 （真操作：不用嘴巴保證，直接在執行期把載入的模型參數印出來做三方對帳。）

至於「全精度為什麼還這麼快」（25 秒音檔只算 23 秒）：

白話比喻：fp32 像「算帳時每個數字都寫到小數點後很多位」，是會慢一點、佔比較多紙；但你的 M 系列晶片本來就是為了大量平行計算設計的，多寫幾位對它只是多動點肌肉，不是換一顆更慢的腦。 （真操作：瓶頸不在精度而在記憶體頻寬；M 系列統一記憶體頻寬高，6GB 模型沒有一般 PC「CPU↔獨顯走 PCIe」的搬運瓶頸。且 25s < chunk_length_s=28，只跑一個窗口、一趟 encoder + 一趟 decode 就結束；丟 10 分鐘檔時間才會近似線性拉長。）

v5 — 「發布給同事下載」時抓出的隱蔽缺口（本次最有價值的一步）

白話比喻：你把新版菜單發下去，客人看到菜單上多了新菜就點了——但廚房的師傅還沒學會這道菜，一點就退單。菜單（前端）跟廚房（後端）各自更新、卻沒對齊，就會發生「看得到、點不到」。 （真操作：lua 前端會每 4 小時自動更新，同事會拿到含 Breeze 選單的新版；但既有的 ensureLwmScriptsDeployed 舊邏輯只在 daemon 檔案不存在時才抓，同事機器上已存在的 lwm_daemon.py 停在 1.9.0，不認得 breeze → 一選就回 400 unsupported model。）
白話比喻（順手把安裝門檻也降到最低）：新同事不該還要研究安裝步驟，把「複製這一行貼上去」放在說明書封面第一行。 （真操作：README.md 標題正下方置頂 curl -fsSL https://raw.githubusercontent.com/botrun/botrun-hammer/main/install.sh | bash；lua 版本 1.11.0 → 1.11.1。）

三、成果四件套

① 最終 How-to（同事怎麼用）

對象要做什麼結果
新同事貼上 README 第一行的 curl 安裝直接是 v1.11.1 + daemon 1.11.0，按 F6 就有 Breeze 選項
既有同事什麼都不用做lua 每 4h 自動更新；下次切本機引擎時 daemon 自動升級到認得 Breeze
第一次用 Breeze選 💻 本機 Breeze-ASR-26 (台語・全精度)自動下載模型約 6.2GB + lazy 裝 transformers/torch，之後 fp32 本機轉錄

② 最終程式碼（關鍵片段）

# lwm_daemon.py — BreezeBackend：官方僅 F32，故走 transformers fp32
if torch.backends.mps.is_available():
    device, dtype = "mps", torch.float32     # 全精度：MPS 一律 fp32
elif torch.cuda.is_available():
    device, dtype = "cuda", torch.float16
else:
    device, dtype = "cpu", torch.float32
self._pipe = pipeline("automatic-speech-recognition",
    model=repo, torch_dtype=dtype, device=device,
    chunk_length_s=28)                        # <30s 窗口，長音檔自動切塊
-- botrun-hammer.lua — daemon 不只「缺檔才補」，版本落後就重部署 + 重啟
local ver = installedDaemonVersion(dest)
if ver ~= LWM_DAEMON_REQUIRED_VERSION then   -- 期望 1.11.0
  stale = true                               -- 重抓 GitHub raw 覆蓋
end
-- 若 daemon.py 被更新且正在跑 → ctl.sh restart 載入新程式碼

③ 最終 prompt（可重用的一句話需求範式）

「多支援 <模型> <精度> for local mac，先掃描原本的程式碼再支援」——先要求對齊既有架構、再要求精度限定，兩個約束把實作路徑收斂到唯一解。後續「這真的是 fp32 嗎」「下載幾 MB」是把口頭宣稱逼成可驗證事實的健康懷疑。

四、為什麼最後能突破：關鍵變因

節點先前為何會卡關鍵變因（突破點）
選型直覺想沿用 mlx-whisper 快速路徑認清「全精度」＝需求硬約束 → 官方只有 F32 → 唯一解是 transformers fp32
信任「跑很快」讓人懷疑偷偷降精度了用三方對帳（下載/RAM/算術都=6.17GB）把宣稱變鐵證，而非口頭保證
發布以為「把前端推出去」就叫發布完成看見前後端分開更新的縫隙 → 加版本比對自動重部署，讓同事零操作也對齊

五、地雷傳承（索引於 ./CLAUDE.md）

  • L1 「全精度／fp32」是選型硬約束：官方無 MLX 權重時，全精度只能走 transformers PyTorch，別為了套用既有 MLX 路徑而偷偷量化。
  • L2 宣稱精度必須可驗證：執行期印 param.dtype + bytes/param + 三方對帳（磁碟/RAM/算術）；fp32=4、fp16=2、8bit=1、4bit=0.5 bytes/param，一算就露餡。
  • L3 前後端分開更新必須有版本對齊機制：只「缺檔才補」會讓同事拿新前端配舊後端而報錯；改為「版本落後就重抓 + 重啟」。任何自我修復都要從「缺檔判斷」升級為「版本判斷」。
  • L4 MPS 一律 fp32：MPS 對 fp16 部分算子支援不穩，本機全精度直接鎖 fp32 最穩。
  • L5 首次下載體積要誠實標示：F32 未壓縮的 large-v2 約 6.2GB，是常見 fp16 版的兩倍，選單提示別沿用「約 2GB」的舊估。
